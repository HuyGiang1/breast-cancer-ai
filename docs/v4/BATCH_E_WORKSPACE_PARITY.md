# Batch E: Account Types, Secure Doctor Access, Doctor Workspace, Patients, Activity & Reports
## Feature Parity Audit

This document audits the legacy workspace behavior (`5b6c72c5ae1d4cb4e16bb9989dd6adfb49a5d99a`) against the current pre-Batch-E state, analyzes security and scientific boundaries, and defines the Batch E implementation actions.

---

### Parity Table

| Feature | Legacy Behavior (`5b6c72c`) | Current Pre-Batch-E State (`e50ca2c`) | Security & Scientific Compatibility | Batch E Action |
| :--- | :--- | :--- | :--- | :--- |
| **Registration / Account Roles** | Exposed a raw `role` dropdown (`user` or `doctor`) on public registration without verification. | Fixed server to force `role = "user"`, but registration UI still behaves as generic single account. | Critical: Public self-assignment of `doctor` role is a security vulnerability. Authority must be server-side. | Rebuild registration with distinct **Personal / Self-analysis** and **Doctor / Clinician** panels. Server-gate doctor creation via environment-based invite code (`hmac.compare_digest`). Client `role` ignored. |

---

### Architectural Principles
1. **Server Authority**: The backend always dictates permissions and roles. Frontend guards are UX conveniences only.
2. **Deterministic Fallbacks**: Patient lists, activity timelines, and reports render cleanly even if LLM advisors or external services are offline.
3. **Non-Diagnostic Educational Framing**: Neither Personal Activity nor Doctor Workspace makes claims of clinical staging, diagnostic certainty, or autonomous treatment planning.
